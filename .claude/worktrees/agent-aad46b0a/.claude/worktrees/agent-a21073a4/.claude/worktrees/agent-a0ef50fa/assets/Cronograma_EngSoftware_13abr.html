★ Manifesto Ágil — 3/3 provas
EntregasSoftware funcional em ciclos curtos e frequentes > documentação extensa
MudançasÁgil abraza mudanças de requisitos; tradicional congela o escopo
EquipeÁgil: autogerenciáda, papéis flexíveis; Tradicional: hierárquica, papéis rígidos
ClienteColaboração contínua com o cliente durante todo o desenvolvimento
★ Modelos de Processo — 3/3 provas
CascataFases sequenciais rígidas. Só funciona com requisitos bem definidos desde o início
IncrementalEntrega em partes. Ideal quando os requisitos não são totalmente conhecidos
EspiralCiclos com análise de riscos. Incompatível com cronograma fechado no início
PrototipagemVersões rápidas para validação. Útil quando o cliente não sabe o que quer
4ª GeraçãoFerramentas automatizadas. Vantagem: rapidez. Desvantagem: dependência e limitações
Codifica-RemendaAnti-modelo sem planejamento. Gera caos, retrabalho e dívida técnica
★ Requisitos de Software — 3/3 provas
FuncionaisO que o sistema faz. Ex: "permitir login com e-mail e senha"
Não-FuncionaisComo o sistema se comporta. Ex: desempenho, segurança, usabilidade
ImplícitosNão documentados. Causam retrabalho e conflito. Solução: elicitação detalhada
LegaisNão podem ser ignorados mesmo que o cliente peça. A responsabilidade é da equipe
ObservacionaisMais realistas. Pró: captura o comportamento real. Contra: demorado, pode constranger
▲ Natureza do Software — 2/3 provas
Não desgastaSoftware não se deteriora, mas torna-se obsoleto pela evolução do ambiente e tecnologia
ManutençãoO trabalho do engenheiro não termina com a entrega. Manutenção e evolução continuam
Sob encomendaA maior parte do software é desenvolvida sob demanda, não como produto de prateleira
● Gerenciamento — 1/3 provas
Lei de BrooksAdicionar pessoas a projeto atrasado atrasa ainda mais — curva de aprendizado + sobrecarga de comunicação
MitosGerente: "mais gente = mais rápido" • Engenheiro: "entreguei, acabei" • Cliente: "requisito geral basta"
